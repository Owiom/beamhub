# BeamHub как платформа: архитектура и этапы

Документ фиксирует, как расширяем BeamHub от менеджера модов до платформы сообщества,
не переписывая приложение и не ломая то, что уже работает. Обновляется по ходу работ.

## 1. Что есть сейчас

| Слой | Как устроено |
|---|---|
| Интерфейс | нативное окно на tkinter (`core/tkui.py`), тот же API доступен в браузере (`web/`) |
| API | локальный HTTP-сервер на `127.0.0.1:8787` (`app.py`), токен в заголовке, Host/Origin-проверки |
| Данные | SQLite в `%LOCALAPPDATA%\BeamHub\beamhub.db`: каталог, библиотека, избранное, настройки |
| Каталог | 4 провайдера-скрейпера (`core/providers/`), обогащение обложками в фоне |
| Установка | zip проверяется, срезается обёртка, считается SHA-256, кладётся в папку игры; своя папка `mods_disabled` |
| Скачивание | страница мода открывается в браузере, приложение подхватывает файл из «Загрузок» |
| Обновления | сверка версий, уведомления, автообновление самого BeamHub через GitHub Releases |

Сильные стороны, на которые опираемся: строгий локальный API, единый стиль, готовая установка
модов и проверка дубликатов. Слабое место для платформы одно: **общего сервера нет**, все данные
локальные.

## 2. Архитектура платформы

```
┌───────────────────────┐        HTTPS         ┌──────────────────────────┐
│ BeamHub (Windows)     │ ───────────────────► │ Supabase (free tier)     │
│ tkinter + локальный   │  REST + JWT (anon)   │ Postgres + RLS + Auth    │
│ SQLite-кэш каталога   │ ◄─────────────────── │ Google OAuth, Storage    │
└───────────────────────┘                      └──────────────────────────┘
```

- **Локально остаётся всё, что про игру**: каталог, установка, библиотека, обновления.
  ZIP-файлы модов в облако не переносим — только ссылки и метаданные.
- **В облако уходит только общее**: профили, сборки, комментарии, оценки, жалобы, статистика.
- **Доступ к данным** — Supabase REST с `anon`-ключом и RLS-политиками; роль
  (`user` / `moderator` / `admin`) приходит в JWT и проверяется политиками, а не только интерфейсом.
- **Авторизация** — Google через Supabase GoTrue, поток PKCE: приложение поднимает локальный
  обработчик `http://127.0.0.1:<порт>/auth/callback`, открывает системный браузер, получает код
  и меняет его на сессию. Пароли не храним — только токены.
- **Офлайн-режим** — обязателен: без сети работают каталог, установка и библиотека; сборки и
  комментарии показывают «нет связи», а не падают.

Почему Supabase: бесплатный тариф даёт Postgres, авторизацию с Google, RLS, сторедж для аватарок
и обложек, REST без своего сервера. Ограничения free tier (500 МБ БД, 1 ГБ файлов, 50k MAU)
для нашего объёма избыточны. Альтернатива — Firebase (нет Postgres/RLS) и собственный VPS
(платно и требует обслуживания), поэтому не берём.

**Честно об ограничениях**: без своего сервера нельзя гарантировать идеальную защиту от накрутки —
Supabase даёт лимиты и политики, но хитрый пользователь с несколькими Google-аккаунтами обойдёт
их. Поэтому в статистике разделяем «скачивание» (клик по странице мода) и «установку»
(факт появления файла в библиотеке), а рейтинг считаем по уникальным парам «пользователь-сборка»
и показываем отметку «установил через BeamHub».

## 3. Модель данных (облако и локальная копия одинаковы по смыслу)

| Таблица | Назначение |
|---|---|
| `users` | профиль: id, email, никнейм, аватар, описание, роль, провайдер (`google`) |
| `follows` | подписки: кто на кого |
| `collections` | сборка: название, описание, обложка, категория, теги, автор, статус (черновик/опубликована), счётчики |
| `collection_items` | состав сборки: сборка + мод + позиция + заметка |
| `collection_versions` | история: номер версии, снимок состава, что изменилось |
| `comments` | комментарии и ответы (parent_id), к сборкам и модам |
| `ratings` | 1–5 звёзд + отзыв, по одной записи на пару (объект, пользователь), флаг «установил» |
| `reports` | жалобы на комментарии, сборки, пользователей |
| `admin_actions` | журнал действий модерации |
| `stats_events` | события: просмотр / скачивание / установка (раздельно) |

Локально те же таблицы живут в существующей SQLite — чтобы приложение работало без сети и
могло синхронизироваться позже.

## 4. Этапы

| Этап | Что делаем | Готово, когда |
|---|---|---|
| **0** | План, схема, заготовки модулей | документ + схема БД применяется без ошибок |
| **1** | Аккаунты: локальные профили, сессии, подписки; интерфейс провайдера для Google | регистрация/вход/выход, профиль, подписка — проверено тестами |
| **1b** | Google OAuth через Supabase (нужны ключи от вас) | вход через Google в приложении, сессия переживает перезапуск |
| **2** | Сборки: CRUD, состав, обложка, теги, публикация, история версий | создать → добавить моды → опубликовать → увидеть в списке |
| **3** | Установка сборки: проверка «что уже стоит», очередь установки | кнопка «Установить сборку» ставит недостающее, не качая заново |
| **4** | Комментарии, ответы, оценки, отзывы, отметка «установил» | всё создаётся, редактируется и удаляется владельцем |
| **5** | Модерация: жалобы, лимиты, блокировки, панель, журнал | модератор видит очередь и применяет действия |
| **6** | Статистика: просмотры, скачивания, установки, топы, активность | цифры раздельные, видны в профиле и админке |
| **7** | Рекомендации и совместимость | «популярное/новинки/похожие», версии и доступность файлов |

После каждого этапа: `py tests\test_install.py`, `py tests\test_platform.py`,
`py tools\lint_claims.py`, запуск приложения и проверка сценария вручную.

## 4a. Состояние работ

| Этап | Статус | Что проверено |
|---|---|---|
| 0. План и схема | готово | таблицы платформы создаются в существующей SQLite |
| 1. Аккаунты (локальные) | готово | регистрация, вход, выход, профиль, подписки — `tests/test_platform.py` |
| 2. Сборки | готово | создание, состав, теги, черновик/публикация, история версий, списки |
| 3. Установка сборки | готово | план «что уже стоит», кнопка ставит недостающее по одному моду |
| 1b. Google через Supabase | ждёт ключей | инструкция ниже |
| 4. Комментарии и оценки | схема готова | таблицы `comments`, `ratings` созданы, API — следующий этап |
| 5. Модерация | схема готова | `reports`, `admin_actions`, блокировки аккаунтов в `accounts.set_blocked` |
| 6. Статистика | частично | `collections.stats()`: пользователи, установки, топ модов и сборок, активность |
| 7. Рекомендации | в плане | популярное/новинки уже в списках сборок; похожие моды — далее |


## 5. Что нужно от вас (этап 1b)

1. Создать проект на [supabase.com](https://supabase.com) (бесплатный тариф).
2. В **Authentication → Providers → Google** включить провайдера и вставить Client ID/Secret
   из [Google Cloud Console](https://console.cloud.google.com/apis/credentials):
   - тип «OAuth client ID» → «Desktop app» или «Web application»;
   - redirect URI: `https://<project>.supabase.co/auth/v1/callback`.
3. В **Authentication → URL Configuration → Redirect URLs** добавить
   `http://127.0.0.1:8787/api/auth/callback` (и `http://localhost:8787/api/auth/callback`).
4. Прислать **Project URL** и **anon public key** (это публичные значения, секретов не нужно).
   `service_role` **не присылать** — он не должен попадать в приложение.
5. Выполнить SQL-миграцию, которую я подготовлю в `supabase/schema.sql`, в SQL Editor.

После этого я переключаю провайдера авторизации с локального на Google и проверяю вход.

## 6. Правила, которых держимся

- ZIP-моды и папка игры остаются локальными; в облаке только ссылки и метаданные.
- Никаких платных API: Supabase free, Google OAuth free, рекомендации — свои алгоритмы.
- Не заявляем «совместимость подтверждена», если её никто не проверял: пишем «заявлена автором»
  и «проверено BeamHub» только там, где есть факт установки.
- Локальные функции работают без аккаунта и без сети.
